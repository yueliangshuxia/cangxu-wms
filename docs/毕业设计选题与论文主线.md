## 二、一句话主线

> **以“货位分配靠经验、拣货距离长”为切口，用订单关联分析和 AHP-TOPSIS 把上架决策变得可解释，再把方法嵌进一套完整的仓储管理系统，用历史订单仿真证明它确实减少了拣货距离。**

整篇论文围绕这条线展开，所有章节都回答同一个问题：**“为什么这样上架，比凭经验上架更好？”**

### 五步叙事

1. **痛点**：仓库里“货放哪里”主要靠老员工经验；热销品放得远、关联商品分散，拣货员每天多走很多路；库存、库位、设备数据又分散在不同系统。
2. **系统**：先做一套完整的 WMS（Spring Boot + Vue + MySQL），覆盖入库、出库、库存、库位、盘点、退货、设备监控、权限与审计，让业务真正跑起来。
3. **方法**：在系统内部用 Apriori 从历史订单里挖出“经常一起出库”的商品关系，用 AHP 确定周转率、订单相关性、拣货距离、体积适配四项指标权重，再用 TOPSIS 给候选库位打分排序，接进入库上架流程。
4. **实验**：用同一批历史订单，对比随机上架、ABC 分类、AHP-TOPSIS 三种策略的平均拣货距离、订单履行时间、库位利用率。
5. **闭环**：上架推荐 → 出库波次 → 作业数据回流 → 权重和规则迭代。系统不是算法的演示壳，算法也不是系统的装饰。

## 三、论文结构（7 章）

参考论文采用“需求分析 → 总体设计 → 数据库 → 详细实现 → 应用展示 → 测试”的工程型写法。本题也是工程型，第 5 章是系统主体；第 4 章单独留给 AHP-TOPSIS 货位优化，作为系统的核心模块，避免论文变成纯 CRUD 说明书。

### 第 1 章 绪论

- 1.1 研究背景与行业痛点
  - 仓储从“人找货”到“货到人”的演进
  - 四个痛点：货位靠经验、拣货路径长、库存信息滞后、设备数据孤岛
- 1.2 国内外研究现状
  - WMS 与智能仓储
  - 货位优化：ABC 分类、关联规则、智能优化算法
  - 多准则决策：AHP、TOPSIS 在物流选址/评价中的应用
  - 物联网在仓储中的应用
- 1.3 研究目标与意义
- 1.4 研究内容与论文结构
- 1.5 本章小结

**写作要点**：痛点要落到“可被你的系统解决”的程度。不要泛泛写“物流行业快速发展”，要写“某类 SKU 上架位置靠经验，导致平均拣货距离高”。

### 第 2 章 相关技术与理论基础

- 2.1 智能仓储与 WMS 概述
- 2.2 AHP 层次分析法
  - 判断矩阵、特征向量、一致性检验（CR < 0.1）
- 2.3 TOPSIS 逼近理想解排序法

- 2.4 Apriori 关联规则
  - 支持度、置信度、提升度
- 2.5 系统开发技术
  - Spring Boot、Vue 3、MySQL、Redis、MQTT、ECharts
- 2.6 本章小结

**写作要点**：公式不要堆砌，每个公式后面解释“在本课题里代表什么”。例如 TOPSIS 的贴近度不是数学装饰，而是“候选库位离理想库位有多近”。

- 3.6 本章小结

**写作要点**：这一章要出现“系统总体架构图”和“功能模块图”，和 Demo 的页面结构对应起来。

## 四、创新点怎么写

不要写“用了 Spring Boot 和 Vue 所以创新”。创新点要落在方法和业务结合上：

1. **订单关联 + 多指标货位决策**  
   在传统 ABC 分类只看周转率的基础上，引入 Apriori 订单关联度，避免“热销品各自占好位置、关联品却离得很远”。

2. **把物联网约束纳入货位评价**  
   温敏商品、恒温库区、设备可达性作为约束或指标，而不是把 IoT 只做成一个“温湿度大屏”。

3. **算法嵌入业务闭环**  
   推荐结果直接进入入库上架流程，出库波次再验证效果，形成“推荐—执行—回流”的闭环，而不是离线跑一次实验。

4. **可解释的评分界面**  
   AHP 权重、TOPSIS 贴近度、候选指标全部在界面上可见，仓管员可以理解并人工调整。这一点在答辩时很好讲。

> 如果导师要求“必须有改进”，可以把“订单关联度”作为对传统 AHP-TOPSIS 指标体系的扩展，并做消融实验证明它的贡献；但不要凭空写“改进”，要用实验说话。

## 五、实验设计

### 数据集

优先方案：

- 使用公开供应链数据集（如 Kaggle 的 DataCo Smart Supply Chain）做订单抽取；
- 或使用实习/实验室的脱敏订单数据。

没有真实数据时的可接受方案：

- 基于 200 个 SKU、12,480 条订单做仿真生成；
- 商品销量服从 Zipf 分布，部分商品按“关联簇”共同出现；
- 在论文中明确写“仿真数据”，并说明生成规则，不要伪装成真实数据。

### 对比基线

| 策略 | 说明 |
|---|---|
| 随机上架 | 候选库位随机分配 |
| ABC 分类 | 按周转率分 A/B/C，A 类靠近出库口 |
| AHP-TOPSIS（等权重） | 不使用 AHP，指标等权 |
| AHP-TOPSIS（完整） | Apriori + AHP + TOPSIS |

### 评价指标

- 平均拣货行走距离（m/单）
- 平均订单履行时间（min/单）
- 库位利用率（%）
- 拣货员行走时间（min/班次）
- 波次合并率（可选）

### 实验流程

1. 用历史订单生成“商品—商品”关联矩阵。
2. 对每个 SKU 生成候选库位集合。
3. 分别用四种策略生成上架方案。
4. 用同一批订单序列模拟拣货，累计行走距离与时间。
5. 重复 10 次取均值，做配对 t 检验或 Wilcoxon 检验。
6. 做消融实验与权重敏感性分析。

### 预期结论（写作时用“结果表明”，不要预先编造）

- 相比随机上架，平均拣货距离下降约 15%–20%；
- 相比 ABC 分类，下降约 8%–12%；
- 库位利用率提升约 8–10 个百分点；
- 去掉 Apriori 后效果下降，说明订单关联维度有贡献。

> 当前 `experiments/run_experiment.py` 的实际结果：AHP-TOPSIS 相对随机上架平均拣货距离下降 20.5%，相对 ABC 分类下降约 8.9%，库位利用率提升 9.1 个百分点；详见 `docs/实验报告.md`。论文中以最终脚本输出为准。

## 六、技术栈建议

### 推荐组合

| 层 | 技术 |
|---|---|
| 前端 | Vue 3 + Vite + Vue Router + Pinia + ECharts |

### 如果 Java 不熟

### 算法实现位置

- 系统内：Java 实现 AHP-TOPSIS 和 Apriori，供上架推荐接口调用。
- 实验中：Python（pandas/numpy）做批量仿真和统计检验，导出图表；论文里说明“实验脚本与系统实现使用同一套公式”。
- 不要把算法只放在 Python 脚本里、系统里却写死结果——答辩容易被追问。

## 九、答辩 3 分钟故事线

1. **问题（30 秒）**  
   “仓库里货放哪里主要靠经验，热销品和关联商品经常被放得很远，拣货员每天多走很多路。我的课题就是把这件事变成可计算的决策。”

2. **系统（60 秒）**  
   “我用 Spring Boot + Vue 做了一套完整的 WMS：登录权限、入库、出库、库存、库位、盘点、退货、设备监控和审计日志都能跑。前端是 Vue 3 单页应用，图表和设备曲线都接真实接口。”

3. **方法（60 秒）**  
   “系统里最有特点的是上架推荐：用 Apriori 从历史订单里挖出经常一起出库的商品，用 AHP 给周转率、订单相关性、拣货距离、体积适配四个指标定权重，再用 TOPSIS 给候选库位打分。权重通过一致性检验，结果可解释，不是写死的。”

4. **证据（30 秒）**  
   “用 12,480 条订单做仿真，相比随机上架平均拣货距离下降约 18%，相比 ABC 分类下降约 10%，库位利用率提升约 9 个百分点。去掉订单关联后效果下降，说明这个维度有贡献。”

5. **收尾（20 秒）**  
   “后续可以把权重做成动态的，接入真实传感器和更多设备，也可以探索大模型做补货建议。”

## 十、风险与规避

| 风险 | 规避 |
|---|---|
| 数据不真实，被质疑实验可信度 | 明确写“仿真数据”及生成规则；优先用公开数据集；给出统计检验 |
| 算法只是调库，没有工作量 | 自己实现 AHP/TOPSIS/Apriori；做消融与敏感性分析；解释每个指标的业务含义 |
| IoT 只做成大屏 | 让传感器数据参与业务规则（温区约束、设备离线影响推荐/波次） |
| 系统范围太大做不完 | 先做入库—库存—出库主流程，再做库位图、设备、报表；设置页可以最后做 |
| 大模型题目评测难 | 不作为主选；放在“未来工作” |
| 题目与专业不符 | 工程型标题不影响专业相关性：正文保留 MQTT 虚拟设备与感知层/传输层/平台层/应用层架构，不只是一套 CRUD；答辩时说明“无实物、用模拟器验证链路” |
